# v4dev 修改方案：复用 Observation 恢复多人环境上下文

日期：2026-09-08。状态：**待实施方案**，不是完成报告。

本专项方案由 [薄层整合总计划](V4_THIN_ADAPTER_PLAN.md) 统筹，全部 v3 功能与 Pages 子开关见 [功能矩阵](V4_FEATURE_SWITCH_MATRIX.md)。最新范围包括全量入站与确认出站、独立功能控制及取消未 ACK 队列静默过期。下文保留身份/来源细节，Core 候选字段和能力须以正式合同为准。

配套 Core 方案见 [Core 多人场景接入与提炼修改方案](CORE_MULTIPARTY_REVISION_PLAN.md)。本轮只新增/修订插件仓库的方案文档，不修改插件业务代码或 Core 源码。

## 1. 已确定的方向

1. 环境消息直接采用 Core 定义的 **Observation**。不新增 `EnvironmentMemory` 领域对象，不新增环境事实库，不修改 `role` 为 `ambient`。
2. 群里没触发回复的消息仍可以是 Observation；“是否采集”“本轮是否采用”“是否值得提炼”分别判断。
3. Core 保存原始观察，维护 RecentContext，并执行 Episode/Claim/Relation 等后台加工；插件负责 AstrBot 事件规范化、身份/空间接入、交付和最终上下文组装。
4. 一个持续记忆主体对应一个 Agent，可活动于多个 Space。人格正文修订不改变 Agent；不同主体即使使用同样的人格模板，也不自动共享记忆。
5. 保持 SQLite、单 Runtime、原生轻量 Pages、可选模块和热启停。本地 import `iris_memory_core`，远程使用独立 `iris-memory-sdk`；不分发插件 pip 包。

## 2. 当前代码与目标差异

| 当前实现 | 需要修改 |
| --- | --- |
| `Identity` 同时承载平台路由、说话人及会话信息 | 区分稳定主体、来源空间、参与者身份和本轮请求；保留当前 UMO 作为发送路由 |
| `LocalBackend.scope()` 按“会话/人格”创建 Agent/Space | Agent 按持续主体创建，Space 在该 Agent 下按稳定来源空间创建 |
| 远程配置禁止多个会话共用 Agent | 允许同一 Agent 对应多个不同 Space；继续防止无意将不同来源绑定到同一 Space |
| 采集正文后交付时再解析部分上下文 | 持久保存事件发生时的身份、空间及配置映射版本；首次提交前冻结完整记录 |
| `observe()` 没有填写发言者身份和来源事件字段 | 使用已有 `actor_external_identity_id`、`source_event_id` 等；多人关系采用 Core 新增的版本化结构约定 |
| ContextBuilder 跳过全部 Observation | 从 Core Recent/Recall 选择当前 Space 的缺失环境上下文，按来源去重并保留发言者/时间信息 |
| `cognitive_provider` 非空会明确报错 | Core 新接缝验收后实现宿主认知适配器；此前保持明确阻塞 |
| 一个会话总开关控制多种行为 | Pages 分开设置观察采集、被动上下文采用、主动发送；仍保留一个明确的总停用入口 |

## 3. 身份与空间映射

### 3.1 推荐映射

```text
插件持久主体 subject_key = iris-main
    → Core Agent A
        → Space S1：QQ 群 1
        → Space S2：QQ 群 2
        → Space S3：某直播间
        → Space S4：与某用户的私聊
```

| 键 | 规则 |
| --- | --- |
| `subject_key` | 插件生成并持久保存；初版可为每个插件人格建立一个默认主体，保留“克隆为独立主体”的区分；不包含群 ID、人格 revision 或正文哈希 |
| `source_space_key` | 根据平台身份命名空间、群/房间/私聊对端及空间类型生成；名称、UMO、重启时间不作为唯一来源 |
| Core Space 绑定键 | `(subject_key, source_space_key)`；同一主体的一组空间不会产生多个 Agent |
| 用户身份键 | `(provider, realm, external_id)`；遵循平台 ID 的实际作用域，不按昵称或文本相似度合并 |
| 适配器实例 | 表示接收和发送的连接实例；与平台身份命名空间分开。只有明确证明来源相同时才合并多个连接的来源键 |
| Session | 有明确平台会话/直播场次时映射；普通群聊首版采用 Space 级观察，省略 `session_id`，不把每次 LLM 请求造为 Session |

直播一场可以对应 Session；主播下一次开播仍使用相同 Space。没有场次信息时可先使用 Space 级观察，不能用连接重连时间推断新现实场次。

同一主体的所有 Space 使用同一份发布人格。若不同群需要相互冲突的完整人格，应选择不同主体/Agent；不能轮流改写同一个 Agent 的 Persona Current。人格模块关闭只影响宿主采用，不撤销观察所属主体或把观察改归 default。

### 3.2 插件本地控制数据

继续使用一个插件 SQLite，增加受版本管理的映射记录：主体→Agent、主体/来源→Space、可选 Session、来源→发送路由、身份→Core 身份引用及缓存版本。

这些是接入与路由数据，不是第二份记忆。已确认的 Observation 正文只在交付队列短暂保留；Core ACK 后保留必要回执和水位，按有界策略清理。

身份注册缓存必须有数量和寿命上限，不能把直播间所有历史用户永久加载到内存；Core 注册与授权恢复也不能依赖插件内存中的无限集合。

## 4. 采集链路

### 4.1 保留结构化事件

`main.py` 的事件 Hook 先调用轻量规范化函数，保留原始正文及结构，不用“张三说：正文”的拼接替代身份字段。

| 信息 | 插件行为 | Core 接缝 |
| --- | --- | --- |
| 发言者 | 提取平台稳定身份，通过公开方法解析/注册 | 现有 `actor_external_identity_id`；Core 解析发生时 Entity，不信任单独的内部 Entity ID |
| 名称 | 保存当时的显示名快照 | 仅用于显示/理解，不能决定身份、权限或事实主体 |
| 来源事件 | 用平台消息 ID 加来源命名空间形成稳定 `source_event_id` | 复用现有来源去重；跨群同号不可冲突 |
| 顺序 | 只有平台确有可复用顺序游标时发送 stream/cursor | 不把当前时间或 UUID 伪装成连续 Cursor |
| 回复对象 | 保存平台回复引用，Core 按授权来源解析 | 拟新增 `structured_payload.interaction` 版本化约定 |
| @ 与指向对象 | 保存明确平台 @/直接寻址信号 | 同上；昵称文字匹配只能标为未解析文本提及 |
| Iris 关系 | 保存当时可确认的“被 @ /直接询问/回复 Iris”信号 | 后来参与的事实由新助手 Observation/回复关系表达，不改写先前旁观消息 |
| 时间 | 保存平台发生时间及宿主首次确认接收时间 | 明确时间可信度；异常源时间保留原值与诊断，规范值按声明策略处理，不用重试时间重写 |
| 图片/附件 | 原事件保留附件引用；可选解析结果明确标记为模型推断 | 派生描述引用原观察，不伪装成人类原话，不再次成为独立佐证 |

缺失身份时允许按契约保存未归属观察；页面记录该缺失。不能统一指定为最后发言者、默认用户或 Iris 自己。名字相同的两个人必须保持不同身份。

转发消息必须区分“当前转发者”“可验证的原作者”和“引用文本中声称的作者”；未知原作者不注册为已验证身份。引用目标尚未到达时保留未解析引用，不能跨 Space 擅自抓取原文。

### 4.2 角色与事件语义

- 群成员、主播、观众的人类消息沿用 `role=user`，文字沿用 `kind=message.text`；是否被机器人回复不改变角色。
- Iris 自己实际生效的输出才使用 `assistant`。其他机器人可作为具名外部参与者，不能冒充本 Agent 助手。
- 礼物、入场等有真实平台记录的事件按 Core 约定使用 `external` 及有明确版本的 kind/payload；第一批插件实现不要求新增 AstrBot 尚无适配器的直播平台。
- 模型生成结束不代表成功发送。继续按现有 Core 效果证明规则处理助手输出，失败/未知结果不补为 committed Observation。

### 4.3 Outbox 与幂等

接收时持久保存规范化事件、主体/来源绑定版本、原始时间、源 ID 和转换版本。异步解析取得 Core 引用后，在第一次网络提交前冻结完整请求及指纹；未知结果重试必须使用同一记录和幂等键。

同一源事件不能因后来开启上下文、被提及或重新连接而再次入库。不能用正文哈希作为消息唯一性：不同人说相同的话、同一个人隔一段时间再说一次，仍是不同事件。平台无稳定 ID 时，只保证本次宿主已分配事件的重试幂等，明确无法保证跨连接全局去重。

消息编辑/撤回需要 Core 受控修订/撤销语义；不能拿相同幂等键提交不同正文，也不能直接覆写旧观察。该公共操作未提供时明确报告不支持，禁止静默留下“已经同步撤回”的假状态。

批量提交按 Agent、Space 和兼容的租约/来源授权分组，限制条数、字节和等待时间。原始事件逐条保留，不把多个人的话拼成一条 `user` 记录。每个批次的请求体和键一旦用于发送就固定；失败隔离和拆批须先区分确定拒绝与结果未知。

获得持久 ACK 不意味着索引或提炼完成。记录各 Space 的接收水位、提交水位和派生进度；同一轮需要 read-your-writes 时使用 Core 已有最低水位能力，超时明确降级，不无限等待后台模型。

## 5. 恢复近期环境上下文

### 5.1 通过 Core 的公开 Observation 上下文及 Recall 获取

移除“所有 Observation 都排除”的规则。2026-09-08 的 Core 工作区新增了 `observation-context.v1`、`observation_context()` 与原文/摘要查询合同，优先消费经安装物验证后的这一入口；长期记忆仍走 Recall。旧 Recent 能力不能代替新能力协商。具体字段以冻结合同为准，不把尚未支持的参与者过滤参数直接发送给接口。

请求使用稳定 Agent、当前 Space、可选 Session。明确回复对象/相关参与者用于解释和后续公共合同，不遍历群成员全名单。

Core 提供近期观察的来源 ID、发言者安全标签、时间、回复关系、修订和摘要覆盖引用。若当前候选缺少这些信息，先要求 Core 补公共返回；不由插件逐条打开 Core 数据库补字段。

普通群聊用 Space 级近期窗口；直播场次可以优先 Session 窗口，并明确是否允许补充同一 Space 的其他窗口。Session 省略不是跨空间通配符，不能修改现有 Scope null 语义来“找齐历史”。

### 5.2 与宿主历史共存

1. 保留系统规则、完整人格、宿主历史、当前输入和工具。
2. 用 Core/source event ID 识别当前输入与宿主已覆盖消息；可靠映射缺失时标注去重精度，不用模糊文本匹配删除不同人的相同发言。
3. 对环境消息保留最小完整回复链，按时间呈现，明确标注发言者、观察时间和“原始发言”的性质。
4. 已有事实纠正与旧发言并存时，将历史发言作为过去发生的记录；优先提供当前有效 Claim，必要时省略容易误导的旧片段，不把旧话重新当作最新事实。
5. 摘要覆盖部分宿主历史时不能整段删除；使用 Core 提供的覆盖引用/紧凑片段，无法无损拆分时保留一个明确的有界选择，不临时调用模型重写摘要。
6. 近期观察与长期候选共享总预算，采用软优先级；短窗口有上限，但空类别可以让出预算。不得重新引入 L1/L2/L3 多套固定字符截断。
7. Recall 候选选择走现有 Usage；新原文查询若不提供候选 ID/Usage 合同，只记录本地选择诊断，不伪造 Recall 候选。“模型可见”不写成“用户已收到”或“模型必定采用”。

示意输出是模型参考数据，不是附加系统指令：

```text
同一群的近期观察：
14:02 张三〔参与者 A〕：我不喝咖啡，喜欢茶。
14:03 李四〔参与者 B，回复 A〕：下次给你带茶。
当前用户随后询问 Iris：刚才他们在聊什么？
```

正式渲染必须转义正文和显示名，保存来源引用；这里的展示标签不代替 Core 的稳定实体或证据 ID。

## 6. 自动总结与事实提炼接入

摘要与事实提炼分别以其 Core 公共合同和安装物验收为门槛；先验证无模型原文接入/查询，不要求等 C1～C3 全部完成才接入。多人事实提炼依然需要主体与候选 Scope 绑定：

- 在 `host.py` 实现新认知输入版本的宿主 Provider 适配，替换当前阻塞分支；本地借用 AstrBot 模型，远程由服务端配置模型，不复制宿主凭据。
- 插件只把 Core 裁剪后的输入交给模型，并按公共候选 schema 返回；不在插件内确定 tenant/Agent 授权、不生成 Binding、不直接落 Core 事实。
- 总结、事实提炼、索引调度和有价值信息筛选均在 Core；已有维护模块低频调用公开有界 `run_pending()`，不再建第二套梦境调度器。
- 认知、图片、人格草稿与其他插件额外模型调用共用预算；远程 Core 的预算由 Core 自己负责，Pages 区分两个预算范围。
- Provider 不可用时观察仍可保存，近期环境仍可读取，后台状态显示待处理/失败。不能将“没有模型”显示为“提炼完成但没有事实”。

## 7. Pages、工具与热加载

配置仍只在 Pages，JSON Schema 继续只有 `core_mode`。增加或调整：

| 页面 | 操作/信息 |
| --- | --- |
| 配置/主体 | 人格所属持续主体、Core Agent、配置修订和绑定状态 |
| 来源空间 | 群/私聊/已支持房间的 Space 映射；分别开启采集、被动上下文、主动发送 |
| 记忆 | Recent 观察查看、明确参与者选择、来源/时间/提炼进度；原文与 Claim 区分展示 |
| 交付诊断 | 来源缺失、身份未解析、引用未解析、积压、截流/过期数量、租约/权限错误 |

`/iris status` 增加主体与 Space 状态。Pages 的“替某人记住”操作必须显式选择参与者或有明确本轮说话人，不能默认拿群内最近一个人的 ID。LLM 记忆工具同样保留事实主体与当前请求者的区别。

热停时取消该模块的新任务，保存有界交付状态。映射改变使用配置 CAS：未发出的事件仍保留发生时归属；发生权限撤销时停止交付并报告，不能为了发送成功把旧事件改归新 Agent。删除、停用、解除绑定分别定义，不自动清除或合并历史记忆。

多人格/多 Space 共用 Agent 后，人格镜像按 Agent 串行和 CAS 校验；不同实例不能互相反复覆盖。主动租约依照 Core 新契约处理，不因为旁观消息而抢占别处的发言权。

| P3 | 消费 Core C5：近期上下文与来源信息 | 没触发回复的讨论也能被后续问题引用，预算/去重/删除规则成立 |

P1 能独立推进，不应因此声称全部链路完成。P2～P5 必须以对应 Core/SDK 安装产物测试为前提，不靠插件私有访问或临时 HTTP 代理补接口。

## 10. 验收场景

至少包括：

1. 两名群成员闲聊且未 @ Iris；第三人询问“刚才说什么”，能得到同群背景；同时证明没有依赖宿主已保存那段历史。
2. 张三说“我喜欢茶”，李四说“我喜欢咖啡”：分别提炼为对应 Entity 的 Claim，不归到 Iris 或提问者。
3. 同名不同 ID、改昵称、QQ 场景 openid 与直播昵称不误合并；只有昵称的引用保持未解析。
4. 同 Agent 的群 A、群 B、直播间：Agent 相同、Space 不同，原文不互串；同群新 Session 的补充行为有明确范围。
5. 消息重复、乱序、回复对象迟到、重连游标重置：不重复事实、不错误合并；不能恢复的缺口有诊断。
6. 当场提问紧跟新消息，Core 投影落后：满足最低水位或明确降级，不无限等待模型，也不伪造空结果。
7. 提炼期间用户撤回来源/身份重绑：按 Core 版本和授权规则拒绝旧候选或重试，不误归属。
8. 原始旧偏好与最新纠正同时存在：近期背景不覆盖当前有效事实；遗忘后相关派生引用重新校验。
9. Provider 超时、预算耗尽、队列满、热停和模式变更：明确状态、队列有界、重试请求不变、无隐式跨库写入。
10. SDK→真实 HTTP→Core 与 Embedded 使用同一组多人用例；清洁依赖安装、真实 AstrBot 群聊/私聊和长稳分别记录证据。

## 11. 数据与兼容

当前开发版的“每会话一个 Agent”不能自动改成合并历史：Agent、Persona Current、Space、来源证据、Task/Focus 和授权都有引用关系。

升级先生成映射预览，保留旧映射及数据；新主体方案可以先用于新来源。旧数据合并需要独立迁移设计、备份、幂等和回退验收，不通过批量改 ID、把 Scope 置空或共享旧 Space 实现。

本专项方案覆盖 v3 L1 的消息接收、近期理解和自动沉淀价值，不恢复三段 FIFO 的具体实现。群聊主动插话、黑话学习和 v3 数据迁移由新的总计划及功能矩阵安排；它们仍未实施，并非移出范围。
